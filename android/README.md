# The ProBeing Android wrapper

A **Trusted Web Activity**: an Android app whose whole content is the ProBeing
PWA, running in the phone's own Chrome. It exists for one reason — a real
home-screen widget — and it adds one screen of its own, for pairing that widget.

Generated by [Bubblewrap](https://github.com/GoogleChromeLabs/bubblewrap) from
the live web manifest at
`https://saad-jameel.github.io/probeing/manifest.webmanifest`, then extended by
hand. `twa-manifest.json` is the input that generated everything else.

## Why a TWA and not Capacitor

A Capacitor app is a plain Android WebView, and a WebView has **no push
notifications and no `showNotification` at all** — the whole of Stage 7a and 7b
would simply not run inside it. Its storage is also separate from Chrome's, so
the app would open to an empty sign-in and a lost push subscription.

A TWA is the same Chrome, on the same origin, with the same storage, the same
service worker and the same push subscription. Installing it changes nothing
about how the PWA behaves; it only adds an icon, a widget, and a launcher
shortcut.

## READ THIS BEFORE RUNNING `bubblewrap update`

**`bubblewrap update` DELETES THE ENTIRE `app/` DIRECTORY before it regenerates
anything.** Not "overwrites some files" — deletes the tree, recursively, with no
prompt and no backup.

`cmds/shared.js` calls `removeTwaProject()` first, and
`core/dist/lib/TwaGenerator.js` maps a recursive `rmdir` over
`DELETE_PROJECT_FILE_LIST`:

```js
['settings.gradle','gradle.properties','build.gradle',
 'gradlew','gradlew.bat','store_icon.png','gradle/','app/']
```

`app/` is in that list. **Every one of the widget's files lives under `app/`** —
the six `glance/` sources, the four layouts, `glance_widget_info.xml`,
`glance_background.xml`, `values/glance.xml`, `values-v31/glance.xml`, and the
hand-edited `AndroidManifest.xml`. They all go. The regenerated project then
builds perfectly, without a widget in it.

**Recovery is `git checkout android/` — and that only works if it was committed
first.** Commit before updating. There is nothing else to fall back on.

What comes back after an update is Bubblewrap's own file set, from its
`COPY_FILE_LIST`, `TEMPLATE_FILE_LIST` and `JAVA_FILE_LIST`:

| Overwritten | What is lost |
|---|---|
| `app/src/main/AndroidManifest.xml` | the `<receiver>`, the `<activity>`, and `INTERNET` |
| `app/build.gradle` | the `signingConfigs` block and the keystore reading |
| `build.gradle` (root) | the added `mavenCentral()` |
| `app/src/main/res/xml/shortcuts.xml` | regenerated at **every build**, not just on update |
| `res/values/colors.xml`, `res/values/strings.xml` | — (the widget deliberately uses `res/values/glance.xml` instead) |
| `LauncherActivity.java`, `Application.java`, `DelegationService.java` | — (nothing of ours lives in them) |

**An earlier version of this file claimed the glance sources were "untouched by
the generator" and that an update "costs three edits rather than a rewrite".
That was wrong, and wrong in the direction that loses work** — it would have
talked someone into running `update` on an uncommitted tree. Giving the widget's
files names Bubblewrap does not know about keeps them from being *overwritten*;
it does nothing about a recursive delete of the directory above them.

Every hand-made edit inside a generated file is marked `ADDED BY HAND (Stage 8)`,
so `grep -rn "ADDED BY HAND" android/` finds them all. After an update that grep
returns nothing — which is the symptom, not the cause.

**Shortcuts are not edited here.** `app/build.gradle` has a `generateShorcutsFile`
task that rewrites `res/xml/shortcuts.xml` from `twaManifest.shortcuts` on every
single build. The only durable place to change them is the `shortcuts` array in
`twa-manifest.json`.

## What the widget does

```
  Working on: NeuraVue                     ↻
  Mon 4h 20m · 3 M · 4/5 prayers
  as of 5:42 PM
```

**Made taller, it lists every open project with its sub-tasks** (version 3), in
place of the "Working on" line:

```
  Working on:                              ↻
  - tail skill
      - write the parser
  - OneNet
  Mon 4h 20m · 3 M · 4/5 prayers
  as of 5:42 PM
```

The server writes the list (`glanceList()` in `_shared/day.js`, capped at 4
projects and 3 sub-tasks each). `GlanceWidget` picks `glance_widget_list.xml`
when at least three list lines fit the widget's height, and the two-line layout
otherwise or when nothing is open. The notification shade keeps its two lines.

**Look-only, by decision.** No M button, no Prayer button, no voice. Tapping it
opens ProBeing. The device secret it stores can do exactly one thing: call
`glance_for(secret)` and receive two lines of text. It cannot write a row, and it
cannot read the `events` table.

That is the trade against rule 4 ("every logging action stays under 5 seconds").
A widget button would beat five seconds — which is the temptation — but it needs
a credential that can *write*, sitting in an APK, reachable from a lock screen.
Logging from the home screen needs its own decision about what such a secret may
do; it is not a button to add to this one.

### Freshness, which is the part that matters

Stage 7b's rule: **a figure must never look fresher than it is.** The widget
renders the `as_of` the server hands it and never extrapolates.

**After two hours the figures are replaced by words** — "These figures are 3
hours old — open ProBeing to refresh." A number on a home screen reads as
current no matter what is printed underneath it.

This means the widget goes quiet for much of the day, and that is honest rather
than broken: the reading only moves when ProBeing itself is open. Saad has been
told the widget is only ever as fresh as the last time the app was open.

### When it refreshes

1. **Every 30 minutes** — Android's floor. Asking for less is silently ignored.
2. **The ↻ chip** — immediate, always works.
3. **On unlocking the phone** — *best-effort only.* Android 8 stopped delivering
   `ACTION_USER_PRESENT` to receivers declared in the manifest, and it is not on
   the exception list, so the only route left is a runtime registration, which
   lives only as long as the app's process. It fires when the process happens to
   be up — common right after using the phone — and not otherwise. The
   alternative is a foreground service holding the process open, which costs a
   permanent notification and battery for a widget that only looks.

### Tap targets

| Tap | Does |
|---|---|
| the two text lines | opens ProBeing — or the pairing screen, when the code is missing or wrong |
| the ↻ chip | fetches again now |
| the "as of" line | opens the pairing screen; this is how to replace a code later |

## Pairing

The secret is typed once, into the pairing screen, from the code ProBeing's own
Settings shows. It is kept in the app's private storage (`MODE_PRIVATE`), is
never written to this repo, and is never logged — not at any level, not inside an
error message, because logcat is readable by a plugged-in laptop.

It is never displayed back either. When a code is already stored the screen says
so in words and leaves the box empty.

## Building

```bash
source ~/.nvm/nvm.sh && nvm use          # Node 22
cd android
./gradlew assembleRelease                # → app/build/outputs/apk/release/app-release.apk
```

Gradle needs two things that are **not** in this repo, both by design:

- `local.properties` with `sdk.dir` pointing at the Android SDK.
- A keystore properties file, mode 0600, holding the signing key's path and
  password. `app/build.gradle` looks for it at
  **`$PROBEING_KEYSTORE_PROPERTIES`**, defaulting to
  `~/.probeing/keystore.properties` resolved from the JVM's own `user.home` —
  so no machine's home directory is baked into this public repo.

  If it is missing, a *release* build now stops immediately with a message
  naming the file and the environment variable. Previously the `exists()` guard
  left `signingConfigs.release` empty while `buildTypes.release` still
  referenced it, and Gradle failed much later complaining that `storeFile` was
  null — which names neither the file nor the reason.

**`twa-manifest.json` also carries a `signingKey.path`, and it is this machine's
absolute path.** That field is read only by `bubblewrap build`, which this
project does not use — `./gradlew assembleRelease` is the build, and it reads the
environment variable above. If you ever do run `bubblewrap build` on another
machine, fix that path first: left wrong, it generates a *new* signing key, and a
new key means a new fingerprint and a published `assetlinks.json` that no longer
matches.

Both are in `.gitignore`, and `scripts/secret_scan.sh` blocks a keystore by
extension, by its magic bytes (so renaming it does not help) and by the password's
own value, in the working tree and in committed history.

## assetlinks.json — public on purpose

`site/.well-known/assetlinks.json` is what tells Chrome that this APK is allowed
to open `saad-jameel.github.io` without a URL bar. **Copy `site/` into the root
of the `saad-jameel.github.io` repository**, so that
`https://saad-jameel.github.io/.well-known/assetlinks.json` serves it. The
`.nojekyll` beside it is required: GitHub Pages skips dot-folders without it.

**The SHA-256 fingerprint in that file is not a secret and must not be removed.**
It is a hash of the *public* certificate, it is meant to be fetched from a public
URL by every phone that installs the app, and it cannot be turned back into a
key. The secret scan is written not to flag it, with a comment saying why, so
nobody "fixes" it later.

Until that file is live the app still works — it falls back to a Custom Tab, which
looks like Chrome with a URL bar across the top. The widget does not care either
way.

## SDK levels, and Android 17

| | |
|---|---|
| `minSdkVersion` | **26** (Android 8.0) |
| `compileSdkVersion` / `targetSdkVersion` | **36** (Android 16) |

Saad's phone runs **Android 17**, and the app is *not* compiled against it. That
is a toolchain limit, established rather than assumed:

- Android 17 ships **minor-versioned** API levels. Google's SDK repository offers
  `platforms;android-37.0`, `37.1` and `37.2` — there is no plain
  `platforms;android-37`. Setting `compileSdkVersion 37` fails outright with
  *"Failed to find Platform SDK with path: platforms;android-37"*, and AGP also
  warns that 37 is past what it supports.
- The Android Gradle Plugin here is **8.9.1**, pinned by Bubblewrap 1.25.0's own
  template. Targeting 37.x needs a newer AGP and Gradle than Bubblewrap ships.

**Targeting 36 on an Android 17 phone is correct, not a compromise.** Android
runs apps that target older levels and applies compatibility behaviour to them;
sideloading imposes no minimum target (the install floor is API 23). If anything
it is the safer side of the trade, because opting in to API 37's behaviour
changes on a device nobody can test against is how a widget quietly stops
updating.

`minSdkVersion` is 26 because `GlanceWords.parseAsOf()` uses `java.time` to read
the server's timestamp, and `java.time` arrives natively at API 26.

## Known limits

- **One launcher shortcut, "Open ProBeing", and no more.** The PWA has no deep
  links: `app.js:showScreen()` is called from tab clicks and nothing else, so a
  "Today" shortcut would land on Home and lie about where it went. Adding hash
  routing to `app.js` is what would make more shortcuts honest.
  (Chrome adds its own "Site settings" entry to that menu; that is Bubblewrap's
  `enableSiteSettingsShortcut`, not ours.)
- **Notification delegation is off.** Turning it on makes Chrome hand the site's
  notifications to this APK to display. Stages 7a and 7b are verified working
  through Chrome, and re-routing a shipped feature through an untested wrapper
  buys the widget nothing. Set `enableNotifications` in `twa-manifest.json` if
  that is ever wanted, and re-verify the 11:30 PM wrapup on a real night.
- The widget shows the `body` line exactly as the server sends it. If that string
  already ends in "· as of 5:42 PM", it will appear twice — once in the body and
  once in the footer, which is where the freshness judgement is added.
